Operations Methodology › Module 2

The Philosophy of GitOps

GitOps leverages developer tools to manage infrastructure and operations configuration.

01

Declarative Systems

The entire desired system state is mathematically described as declarative definitions—typically structured YAML manifests.

02

Git as Source of Truth

All changes pass through version control. Git history becomes the secure, immutable audit trail of who changed what, and when.

03

Continuous Sync

Agents automatically pull approved repository modifications and reconcile states directly onto actual cluster runtimes.

Repository Layout › Module 3.1

Structure of the GitOps Repository

Before writing any code, we establish a robust structural skeleton in our source control management repository.

This visual architecture divides infrastructure components away from operational application orchestrations:

  • clusters/management/: Identifies deployment coordinates mapping to specific OCP clusters.
  • infrastructure/compliance-operator/: Houses all definitions describing namespace isolation, subscriptions, and security parameters.
gitops-foundation/
├── clusters/
│   └── management/
│       └── apps/
│           └── compliance-operator-app.yaml
└── infrastructure/
    └── compliance-operator/
        ├── namespace.yaml
        ├── operator-group.yaml
        └── subscription.yaml
Component Manifests › Module 3.2

The Manifest Elements

1 namespace.yaml

Establishes dedicated memory, computing limits, and turns on cluster monitoring. 

apiVersion: v1
kind: Namespace
metadata:
  name: openshift-compliance
  labels:
    openshift.io/cluster-monitoring: "true"
2 operator-group.yaml

Scopes the operator instance to exclusively manage this newly constructed space. 

apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: compliance-operator
  namespace: openshift-compliance
spec:
  targetNamespaces:
  - openshift-compliance
3 subscription.yaml

References the Red Hat catalog to fetch stable releases and automated patches. 

apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: compliance-operator
  namespace: openshift-compliance
spec:
  channel: "stable"
  installPlanApproval: Automatic
  name: compliance-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
ArgoCD Blueprint › Module 3.3

The Application Manifest

The ArgoCD Application Custom Resource binds your target Git manifests straight onto cluster coordinates.

  • repoURL: Configures where ArgoCD points to monitor updates.
  • path: Navigates downstream configurations to apply.
  • prune & selfHeal: Instructs automatic correction and clean operations during structural deletion events.
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: compliance-operator
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: 'https://github.com/your-org/gitops-foundation.git'
    targetRevision: HEAD
    path: infrastructure/compliance-operator
  destination:
    server: 'https://kubernetes.default.svc'
    namespace: openshift-compliance
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
Interactive Lab › Module 4

Lab: Your First GitOps Application

1
Commit Manifests to Git Structure the directories and push manifests to your primary branch.
2
Bootstrap App onto Cluster Register and deploy the root orchestration layer via terminal CLI.
3
Validate Reconciliation Check the ArgoCD Dashboard and check operator pod orchestration health status. 
# Step 1: Bootstrap the Application definition
$ oc apply -f clusters/management/apps/compliance-operator-app.yaml

# Step 2: Extract ArgoCD admin passwords for UI Login
$ oc extract secret/openshift-gitops-cluster-cluster --to=- -n openshift-gitops

# Step 3: Extract ArgoCD console coordinates URL
$ oc get route openshift-gitops-server -n openshift-gitops -o jsonpath='{.spec.host}'

# Step 4: Verify platform operator health execution
$ oc get pods -n openshift-compliance
